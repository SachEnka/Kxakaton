# Умный кредитный кабинет

Прототип кредитного конвейера для малого и микробизнеса. Клиент проходит путь от потребности до результата, сотрудник банка видит ту же заявку: проверки, оценку и решение.

Подписание и выдача смоделированы на экране. Настоящий ИНН ищется в ЕГРЮЛ (egrul.nalog.ru) и в «Прозрачном бизнесе» (pb.nalog.ru). Кредитную историю бюро по ИНН открыто не отдаёт, поэтому для настоящей компании она не подставляется. Демо-ИНН из таблицы ниже остаются учебными, с синтетической историей. Скоринг — учебная матрица по мотивам Положения Банка России № 590-П, это не расчёт резерва и не IRB.

## Запуск

Нужен Docker. Отдельные Python и Node на машине не требуются.

```text
docker compose up --build
```

Кабинет: http://localhost:8080  
API и Swagger: http://localhost:8000/docs  
Проверка живости: http://localhost:8000/health

Повторный запуск не создаёт вторую копию тестовых пользователей.

## Демо-вход

Пароль у всех учёток: `Demo-2026`

| Email | Что показать |
|---|---|
| `client.good@demo.local` | Оборотный кредит 1 500 000 ₽ на 18 месяцев, ИНН `7700000001`, выручка 800 000 ₽. Итог: одобрение и подписание. |
| `client.offer@demo.local` | 5 000 000 ₽ на 24 месяца, ИНН `7700000002`, выручка 400 000 ₽. Итог: меньшая сумма и более высокая ставка. |
| `client.reject@demo.local` | ИНН `7700000003`. Итог: отказ из-за процедуры банкротства. |
| `client.info@demo.local` | ИНН `7700000005`. Итог: вопрос о выручке молодой компании, затем решение сотрудника. |
| `underwriter@demo.local` | Очередь, факторы, подтверждение или смена решения. |

На экране входа есть кнопки этих учёток. В анкете клиента поля сценария уже подставлены. Дополнительный ИНН `7700000004` даёт отказ из-за просрочки 120 дней.

Короткий сценарий для жюри: войти клиентом «одобрение», нажать «Подобрать продукт», оформить рекомендованный продукт, отправить заявку, перейти к оформлению и подписать. Затем войти сотрудником и открыть эту заявку: там сырые ответы симуляторов и категория качества.

## Что внутри

- `backend` — FastAPI, PostgreSQL, state machine, моки, скоринг.
- `frontend` — два кабинета на React.
- `docs` — архитектура, состояния, модель данных, сценарии, коллекция запросов, пометки о симуляторах.

Конвейер после отправки считается синхронно в API. Очередь сообщений в MVP нет.

## Ограничения

- Подписание и выдача — экранная симуляция.
- Сведения ЕГРЮЛ для настоящего ИНН читаются с egrul.nalog.ru, карточка «Прозрачного бизнеса» — с pb.nalog.ru. Кредитное бюро без согласия компании не вызывается.
- Скоринг — правиловая матрица по мотивам 590-П. Категория качества объясняет решение. Резервы не рассчитываются.

## Как развивать

- Вынести конвейер в фоновый воркер, когда появятся настоящие интеграции.
- Заменить моки адаптерами ЕГРЮЛ и запросом БКИ только при согласии субъекта.
- Подключить открытую модель только чтобы перефразировать уже посчитанное объяснение. Решение по-прежнему считает правиловая модель.

## Проверки

Юнит-тесты скоринга и переходов не требуют базы. Полный прогон, включая сквозные сценарии, выполняется в контейнере API, когда compose уже поднят:

```text
docker compose exec api pytest
```
