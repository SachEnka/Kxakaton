### Если репозиторий приватный

1. На GitHub: **Settings → Collaborators** (для личного репозитория) или **Settings → Collaborators and teams** (для организации).
2. **Add people**, ввести `alfa-hack-2026`, выдать право `Read` (в личном репозитории оно называется read-only).
3. Дождаться, пока аккаунт жюри примет приглашение. Проверить можно в списке collaborators: статус «Pending invite» должен смениться на подтверждённого участника.
4. Дать доступ **до** тега и до отправки жюри ссылки на версию, иначе по ссылке откроется страница 404.

### Если репозиторий публичный

Доступ выдавать не нужно. Достаточно убедиться, что ссылка открывается без входа в аккаунт GitHub (например, в окне инкогнито).

## Идентификатор версии

Версию для жюри определяют два значения: **полный SHA коммита** и **тег**. Название ветки как единственный идентификатор не используется.

### Как получить точный SHA

В чистой копии репозитория, после последнего коммита и `git push`:

```text
git fetch origin
git rev-parse HEAD
git rev-parse origin/main
```

Оба значения должны совпасть. Если нет, локальная ветка и GitHub расходятся: сначала выровняйте их. Проверить, что на GitHub именно этот коммит, можно по ссылке `https://github.com/SachEnka/Kxakaton/commit/<SHA>`.

В жюри передают полный SHA из 40 символов, а не короткую запись.

### Порядок создания финального тега

Тег создаётся только после того, как закончены **оба** этапа подготовки (документация и технический аудит с исправлениями) и владелец дал на это разрешение. Рекомендуемое имя: `alfa-hack-2026-submission`.

1. Убедиться, что рабочая копия чистая: `git status` ничего не показывает.
2. Выполнить `git fetch origin` и убедиться, что `git rev-parse HEAD` совпадает с `git rev-parse origin/main`.
3. Создать аннотированный тег: `git tag -a alfa-hack-2026-submission -m "Alfa Hack 2026 submission"`.
4. Отправить тег: `git push origin alfa-hack-2026-submission`.
5. Выяснить SHA, на который указывает тег: `git rev-parse alfa-hack-2026-submission^{commit}`.
6. Отправить жюри: ссылку на репозиторий, имя тега и SHA из шага 5.

Тег после отправки не переносят. Если пришлось внести правку, создайте новый тег (например, `alfa-hack-2026-submission-2`) и сообщите об этом жюри вместе с новым SHA.

## Как жюри запускает

1. Клонировать репозиторий и перейти на тег или SHA, который указал владелец: `git checkout <тег или SHA>`.
2. Установить Docker Desktop и убедиться, что он запущен.
3. В корне выполнить `docker compose up --build`. На Windows можно запустить `start.bat`: он проверяет Docker, выполняет ту же команду и через несколько секунд открывает кабинет.
4. Дождаться, пока `http://localhost:8000/health` вернёт `{"status":"ok"}`.
5. Открыть кабинет http://localhost:8080. Swagger: http://localhost:8000/docs.

Отдельные Python и Node на машине не нужны. Порты `5432`, `8000`, `8080` должны быть свободны. Первая сборка выкачивает образы Docker и пакеты и требует интернета.

## Процедура проверки жюри

1. Запустить проект (раздел выше).
2. Пройти сценарии из [DEMO.md](DEMO.md). Главный путь: клиент `client.good` оформляет заявку и подписывает, затем сотрудник открывает её в очереди.
3. Сверить результат с ожидаемыми статусами в таблице сценариев DEMO.md. Значения в DEMO.md рассчитаны по коду, а не получены в прогоне приложения. Если результат отличается, это нужно отметить.
4. При желании запустить автотесты в контейнере: `docker compose exec api pytest` (результат в этой работе не получен).
5. Сверить документы и требования: [REQUIREMENTS_CHECKLIST.md](REQUIREMENTS_CHECKLIST.md).

## Что сделать владельцу до сдачи

Эти шаги в рамках подготовки документов не выполнялись.

1. Выполнить `docker compose up --build` и дождаться `health = ok`.
2. Пройти сценарии 1–7 из [DEMO.md](DEMO.md) в браузере и записать фактические результаты (в том числе ставки и платежи).
3. Выполнить `docker compose exec api pytest` и записать результат.
4. Проверить, что подписание и выдача явно названы смоделированными на экранах.
5. Принять решение по найденным дефектам (список в разделе «Известные дефекты» REQUIREMENTS_CHECKLIST.md). Первый по приоритету: сотрудник может вынести решение до окончания конвейера, включая черновик.
6. Подтвердить видимость репозитория и при необходимости выдать доступ аккаунту `alfa-hack-2026`.
7. Закоммитить, отправить и поставить тег по порядку выше.

## Облачная демонстрация

Кейс требует локального Docker. Публичной облачной версии нет, адреса для неё нет, и работоспособность облачного запуска не проверялась. Основной способ проверки: локальный запуск.

Если владелец решит развернуть демо удалённо, нужна машина с Docker и открытыми портами `8080` и `8000`:

```text
git clone https://github.com/SachEnka/Kxakaton.git
cd Kxakaton
docker compose up --build -d
```

Перед публичным размещением нужно заменить демо-секреты (`JWT_SECRET`, пароль базы в `docker-compose.yml`) и ограничить CORS: в `backend/app/main.py` разрешены любые источники, это настройка под локальный показ. Платные API и закрытые LLM не используются.

## Ограничения MVP

- Подписание и выдача денег не выполняются: «Подписать» только меняет статус.
- Скоринг — учебная правиловая матрица по мотивам 590-П, резервы не рассчитываются.
- Для демо-ИНН данные берутся из локальных фикстур. Для настоящего ИНН — из открытых сервисов ФНС, нужен интернет в контейнере `api`; кредитная история не запрашивается.
- Конвейер синхронный, очереди сообщений и автоповтора нет.
- Приложение, автотесты и сквозные сценарии не запускались при подготовке этого пакета.
- Известные дефекты не исправлены (они вынесены на следующий этап).
