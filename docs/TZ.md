# ТЗ. Умный кредитный кабинет предпринимателя

Прототип цифрового кредитного конвейера для малого и микробизнеса (ООО и ИП).
Один веб-продукт: путь клиента от потребности до результата и внутренняя обработка заявки банком.
Статус заявки прозрачен, данные и контекст не теряются между этапами.

Документ — инструкция к реализации. Каждый пункт говорит, что сделать и как именно.

---

## 1. Результат, который должен получиться

Работающий MVP, который жюри запускает у себя и проходит по основному сценарию без устных пояснений.

Обязательные артефакты:

1. Веб-кабинет клиента.
2. Веб-кабинет сотрудника банка.
3. Единый backend со state machine заявки, проверками, скорингом и решением.
4. Локальные моки ЕГРЮЛ/ЕГРИП, БКИ и ФНС «Прозрачный бизнес».
5. `docker compose up` поднимает всё с нуля.
6. README, OpenAPI, коллекция запросов, диаграмма состояний, модель данных, тестовые сценарии, синтетические данные, тестовые учётки.
7. `THIRD_PARTY_NOTICES.md`: какие внешние системы смоделированы и что ответы синтетические.

Вне объёма MVP: реальные интеграции, выдача денег, УКЭП, мобильное приложение, платные API, закрытые модели LLM, полный бэк-офис банка, буквальный расчёт резервов по 590-П.

## 2. Стек и почему он такой

| Часть | Выбор | Как используем |
|---|---|---|
| API | Python 3.12, FastAPI | OpenAPI появляется сам на `/docs`. Вся бизнес-логика здесь. |
| БД | PostgreSQL 16 | Заявка, события, результаты проверок и скоринга. |
| ORM / миграции | SQLAlchemy 2 + Alembic | Схема только через миграции. |
| UI | React + TypeScript + Vite | Два кабинета на одном фронте, разделение по роли. |
| Авторизация | JWT, access-токен | Логин по email и паролю. Роль в токене. |
| Контейнеры | Docker Compose | Сервисы `db`, `api`, `web`. |
| Зависимости | `package-lock.json` и pinned `requirements.txt` | Lock-файлы коммитятся. |

Конвейер после отправки заявки выполняется синхронно внутри API. Отдельная очередь не нужна для демо и не должна ломаться при проверке. В документации это описано как осознанное ограничение MVP: следующий шаг — фоновый воркер.

ИИ на первом контуре — шаблоны объяснений по факторам скоринга. Они всегда объясняют то, что посчитала правиловая модель. Открытая LLM подключается только вторым шагом и только как перефраз уже посчитанного объяснения, без права менять решение.

## 3. Роли

1. **Клиент** — предприниматель. Видит продукты, свою заявку, человекочитаемый статус и результат.
2. **Сотрудник банка** — одна роль вместо оргструктуры. Видит очередь, сырые проверки, факторы скоринга, подтверждает или меняет решение, запрашивает уточнение.
3. **Система** — автоматические переходы: валидация, обогащение, скоринг, предварительное решение.

Сотрудник не видит чужие действия клиента как «магию»: каждое изменение статуса пишется в журнал событий.

## 4. Кредитные продукты

Четыре продукта. Лимиты и ставки зашиты в конфиг `products.yaml`, не размазаны по коду.

| Код | Название | Кому показываем | Сумма | Срок | Базовая ставка |
|---|---|---|---|---|---|
| `TURNOVER` | Оборотный кредит | Пополнение оборотных средств, закупка товара | 300 000–10 000 000 ₽ | 6–36 мес. | 20% |
| `DEVELOPMENT` | Кредит на развитие | Оборудование, ремонт, запуск направления | 500 000–20 000 000 ₽ | 12–60 мес. | 18% |
| `OVERDRAFT` | Овердрафт | Кассовые разрывы | 100 000–3 000 000 ₽ | 3–12 мес. | 22% |
| `LINE` | Кредитная линия | Сумма нужна частями, цель смешанная | 500 000–15 000 000 ₽ | 12–36 мес. | 19% |

Подбор без банковской экспертизы пользователя:

1. Клиент выбирает цель из списка: оборотка, развитие, кассовый разрыв, «пока не знаю».
2. Вводит желаемую сумму и срок.
3. Система предлагает один основной продукт и, если параметры на границе, одну альтернативу.
4. Правило выбора:
   - кассовый разрыв → `OVERDRAFT`;
   - развитие → `DEVELOPMENT`;
   - оборотка → `TURNOVER`;
   - «не знаю» или сумма должна быть гибкой → `LINE`.
5. Если сумма или срок вне коридора продукта, карточка показывает ближайшие допустимые границы и не даёт отправить заведомо невозможные параметры. Клиент может поправить значения на карточке.

Ставка в решении = базовая ставка продукта + надбавка категории качества (раздел 11).

## 5. Экраны клиента

Один сценарий, без лишних разделов.

1. **Вход и регистрация.** Email, пароль, ФИО, телефон. После регистрации клиент попадает в кабинет.
2. **Потребность.** Цель, сумма, срок. Кнопка «Подобрать продукт».
3. **Подбор.** Карточки продуктов: название, для чего, коридор суммы и срока, ставка «от». Рекомендованный продукт отмечен. Короткий текст, почему он подходит. Кнопка «Оформить заявку».
4. **Заявка.** ИНН, форма (ООО/ИП), контактное лицо, выручка в месяц, расходы в месяц, цель ещё раз (уже выбрана), сумма, срок, комментарий. Черновик сохраняется сам. Повторно одни и те же поля не спрашиваются.
5. **Статус.** Вертикальные этапы. У текущего этапа три строки: что уже сделано, что происходит сейчас, кто следующий (вы или банк). Журнал событий простым языком.
6. **Уточнение.** Если статус `NEED_INFO`, на этом же экране форма с конкретным вопросом банка и полем ответа.
7. **Результат.**
   - Одобрено: сумма, срок, ставка, платёж, кнопка «Перейти к оформлению».
   - Другие условия: что изменилось относительно запроса и почему, кнопки «Принять условия» и «Отказаться».
   - Отказ: понятная причина без внутренних кодов, что можно сделать дальше (новая заявка позже, другая сумма).
8. **Оформление.** Экран индивидуальных условий. Кнопка «Подписать» — симуляция. После неё статус «Финансирование оформлено», с текстом, что выдача смоделирована.

Клиентские подписи статусов:

| Технический статус | Текст клиенту |
|---|---|
| `DRAFT` | Черновик |
| `SUBMITTED` | Заявка отправлена |
| `VALIDATING` | Проверяем данные |
| `NEED_INFO` | Нужны уточнения |
| `ENRICHING` | Проверяем сведения о компании |
| `SCORING` | Оцениваем заявку |
| `DECISION_READY` | Готовим решение |
| `APPROVED` | Одобрено |
| `APPROVED_WITH_CHANGES` | Есть предложение с другими условиями |
| `REJECTED` | Отказано |
| `CONTRACTING` | Оформление |
| `ISSUED` | Финансирование оформлено |
| `CANCELLED` | Заявка отменена |

## 6. Экраны сотрудника банка

1. **Очередь.** Таблица заявок: номер, компания, продукт, сумма, статус, дата, признак «ждёт сотрудника».
2. **Карточка заявки.** Всё, что нужно для решения, на одном экране:
   - параметры заявки;
   - ответы трёх моков;
   - категория качества, финансовое положение, обслуживание долга, стоп-факторы, числовой балл;
   - предложенное решение системы;
   - журнал событий.
3. **Действия сотрудника:**
   - подтвердить решение системы;
   - изменить решение (одобрить / одобрить с другими условиями / отказать) с обязательным комментарием;
   - запросить уточнение: текст вопроса уходит клиенту, статус становится `NEED_INFO`.

Автоматическое решение возникает само. Сотрудник обязателен в двух случаях: категория IV и ручной override. Для категорий I–III и V система проводит решение сама, а сотрудник видит его в очереди и может вмешаться.

## 7. Состояния и переходы

Менять статус можно только через модуль `state_machine`. Прямые присваивания в роутерах запрещены. Каждый переход пишет `application_events`.

```text
DRAFT
  → SUBMITTED            клиент отправил заявку
SUBMITTED
  → VALIDATING           система приняла заявку
VALIDATING
  → NEED_INFO            не хватает поля или ИНН не похож на ИНН
  → ENRICHING            комплект данных достаточный
NEED_INFO
  → VALIDATING           клиент прислал ответ
ENRICHING
  → SCORING              три мока ответили и ответы сохранены
SCORING
  → DECISION_READY       балл и категория посчитаны
DECISION_READY
  → APPROVED             категории I–II, сотрудник не требуется
  → APPROVED_WITH_CHANGES категория III, либо IV с жизнеспособным встречным предложением
  → NEED_INFO            категория IV и не хватает данных, вопрос сформулирован
  → REJECTED             категория V или стоп-фактор
APPROVED
  → CONTRACTING          клиент открыл оформление
APPROVED_WITH_CHANGES
  → CONTRACTING          клиент принял новые условия
  → CANCELLED            клиент отказался от новых условий
CONTRACTING
  → ISSUED               клиент нажал «Подписать»
REJECTED, ISSUED, CANCELLED
  конечные статусы
```

Из любого незавершённого статуса сотрудник может перевести заявку в `NEED_INFO`, `APPROVED`, `APPROVED_WITH_CHANGES`, `REJECTED`. Такой переход хранит комментарий и id сотрудника.

Повторный прогон скоринга запускается, когда клиент ответил на уточнение и новые данные влияют на расчёт. Старые проверки и старый скоринг не затираются: пишется новая запись, у заявки остаётся ссылка на актуальную.

## 8. Модель данных

Таблицы:

1. `users` — id, email, password_hash, full_name, phone, role (`CLIENT` | `UNDERWRITER`), created_at.
2. `companies` — id, owner_user_id, inn, ogrn, name, legal_form (`OOO` | `IP`), okved, registration_date, director_name, address, registry_status. Поля реестра заполняет мок ЕГРЮЛ, клиент вводит ИНН и при желании название.
3. `applications` — id, public_number, company_id, product_code, purpose, amount, term_months, monthly_revenue, monthly_expenses, comment, status, created_at, updated_at.
4. `application_events` — id, application_id, from_status, to_status, actor_type (`CLIENT` | `UNDERWRITER` | `SYSTEM`), actor_user_id, message, payload_json, created_at.
5. `external_checks` — id, application_id, source (`EGRUL` | `BKI` | `FNS`), status (`SUCCESS` | `FAILED`), request_json, response_json, created_at.
6. `score_results` — id, application_id, score, financial_position (`GOOD` | `AVERAGE` | `POOR`), debt_service (`GOOD` | `AVERAGE` | `POOR`), quality_category (`I` | `II` | `III` | `IV` | `V`), stop_factors_json, factors_json, decision, offered_amount, offered_term_months, offered_rate, monthly_payment, explanation, created_at.
7. `info_requests` — id, application_id, question, answer, asked_by, answered_at.
8. `contracts` — id, application_id, terms_json, status (`DRAFT` | `SIGNED`), signed_at.

`public_number` — человекочитаемый номер вида `AK-10001`.

Связи: пользователь-клиент владеет компаниями, у компании много заявок, у заявки много событий, много проверок и много расчётов скоринга. Актуальные проверка и скоринг — последние по времени.

## 9. API

Префикс `/api`. Авторизация: `Authorization: Bearer`.

Клиент:

- `POST /auth/register`
- `POST /auth/login`
- `GET /auth/me`
- `POST /applications` — создать черновик
- `PATCH /applications/{id}` — сохранить поля черновика
- `POST /applications/recommend` — цель, сумма, срок → основной продукт и альтернатива
- `POST /applications/{id}/submit`
- `GET /applications`
- `GET /applications/{id}` — заявка, статус, события, актуальное решение, клиентское объяснение
- `POST /applications/{id}/answers` — ответ на уточнение
- `POST /applications/{id}/accept-offer`
- `POST /applications/{id}/decline-offer`
- `POST /applications/{id}/sign`

Сотрудник:

- `GET /underwriter/applications`
- `GET /underwriter/applications/{id}` — плюс сырые моки и факторы
- `POST /underwriter/applications/{id}/confirm`
- `POST /underwriter/applications/{id}/override` — новое решение, сумма, срок, ставка, комментарий
- `POST /underwriter/applications/{id}/request-info` — текст вопроса

Служебное:

- `GET /health`
- OpenAPI: `/docs`, `/openapi.json`

Чужую заявку клиент не читает. Сотрудник читает все. Проверка на каждом эндпоинте.

Коллекция запросов: `docs/api.http` с логином и основным сценарием.

## 10. Моки внешних источников

Отдельный пакет `app/mocks`. Никаких сетевых вызовов. По ИНН возвращается заранее описанный JSON. Неизвестный ИНН получает устойчивый профиль из хеша ИНН, чтобы произвольная заявка тоже проходила конвейер.

Общие правила:

1. Ответ мока сохраняется в `external_checks` целиком.
2. Ошибка мока — редкий тестовый ИНН. Заявка остаётся в `ENRICHING`, в журнал пишется событие, сотрудник видит сбой. Для демо основной путь всегда успешный.
3. В `THIRD_PARTY_NOTICES.md` прямо сказано: это симуляторы ЕГРЮЛ/ЕГРИП, БКИ и ФНС «Прозрачный бизнес». Кредитная история выдумана. Реальный БКИ без согласия субъекта недоступен, и кейс разрешает локальный стаб.

### 10.1. ЕГРЮЛ / ЕГРИП

Вход: ИНН. Выход:

- full_name, short_name, legal_form, ogrn
- status: `ACTIVE` | `LIQUIDATING` | `LIQUIDATED`
- registration_date, okved, okved_name
- address, director_name
- unreliable_address, unreliable_director
- charter_capital

`LIQUIDATED` и `LIQUIDATING` — стоп-фактор.

### 10.2. БКИ

Вход: ИНН. Выход — синтетическая история, не реальный отчёт:

- loans[]: type, opened_on, amount, balance, monthly_payment, overdue_days, status
- active_count, total_debt, total_monthly_payment, max_overdue_days

Просрочка больше 90 дней — стоп-фактор.

### 10.3. ФНС «Прозрачный бизнес» и открытый признак банкротства

Вход: ИНН. Выход:

- tax_regime, employees_count
- income_last_year, expense_last_year
- tax_debt, tax_debt_amount
- suspended_accounts
- bankruptcy_procedure: `null` | `OBSERVATION` | `COMPETITION`

Любая bankruptcy_procedure — стоп-фактор. В документации поле помечено как смоделированная проверка открытого реестра банкротств, упакованная в тот же шаг обогащения.

### 10.4. Зашитые ИНН для демо

| ИНН | Компания | Что должен увидеть жюри |
|---|---|---|
| `7700000001` | ООО «Северная лавка» | Чистое досье, одобрение запрошенных условий |
| `7700000002` | ООО «Волга Трейд» | Нагрузка высокая, встречное предложение с меньшей суммой |

## 11. Скоринг и кредитное решение

Модель правиловая. Она использует логику Положения Банка России № 590-П: финансовое положение, обслуживание долга, категория качества I–V. Это не расчёт резерва и не внутренний рейтинг банка. Формулировка для документации и для экрана сотрудника фиксируется буквально:

> Упрощённая правиловая модель по мотивам 590-П. Категория качества здесь — способ объяснить кредитное решение. Резервы не рассчитываются.

### 11.1. Платёж и долговая нагрузка

Месячная ставка `r = offered_annual_rate / 12`.
Число месяцев `n = term_months`.

Платёж аннуитета:

```text
payment = amount * r * (1 + r) ^ n / ((1 + r) ^ n - 1)
```

Нагрузка:

```text
burden = (bki.total_monthly_payment + payment) / application.monthly_revenue
```

Если выручка не заполнена или равна 0, финансовое положение не считается хорошим, заявка уходит в уточнение.

Обратный расчёт максимальной суммы под целевую нагрузку 0,40:

```text
max_payment = 0.40 * monthly_revenue - bki.total_monthly_payment
max_amount = max_payment * ((1 + r) ^ n - 1) / (r * (1 + r) ^ n)
```

Если `max_payment <= 0`, встречное предложение по сумме невозможно.

### 11.2. Стоп-факторы

Любой стоп сразу даёт категорию V и отказ. Остальные факторы всё равно сохраняются, чтобы сотрудник видел полную картину.

- статус ЕГРЮЛ `LIQUIDATED` или `LIQUIDATING`
- `bankruptcy_procedure` не пустой
- `max_overdue_days > 90`
- приостановление операций по счетам
- сумма заявки больше верхней границы продукта после попытки подбора

### 11.3. Финансовое положение

- **Хорошее.** Компания действующая, возраст от 24 месяцев, выручка указана, налоговой задолженности нет, признаки недостоверности адреса и руководителя выключены.
- **Среднее.** Возраст от 6 до 24 месяцев, либо есть налоговая задолженность меньше 100 000 ₽, либо один признак недостоверности.
- **Плохое.** Возраст меньше 6 месяцев, либо налоговая задолженность от 100 000 ₽, либо оба признака недостоверности, либо выручка не указана.

Возраст считается от `registration_date` мока до даты заявки.

### 11.4. Обслуживание долга

- **Хорошее.** `max_overdue_days = 0` и `burden <= 0.40`.
- **Среднее.** Просрочка от 1 до 30 дней, либо нагрузка от 0.40 до 0.60 включительно.
- **Плохое.** Просрочка от 31 до 90 дней, либо нагрузка выше 0.60.

Нагрузка для этой оценки считается по запрошенным сумме, сроку и базовой ставке продукта.

### 11.5. Категория качества

Матрица положения и обслуживания:

| Финансовое положение \ обслуживание | Хорошее | Среднее | Плохое |
|---|---|---|---|
| Хорошее | I | II | III |
| Среднее | II | III | IV |
| Плохое | III | IV | V |

### 11.6. Решение

| Категория | Решение | Условия |
|---|---|---|
| I | `APPROVED` | Сумма и срок как в заявке. Ставка = базовая. |
| II | `APPROVED` | Сумма и срок как в заявке. Ставка = базовая + 2 п.п. |
| III | `APPROVED_WITH_CHANGES` | Ставка = базовая + 5 п.п. Сумма = минимум из запрошенной и `max_amount`. Срок не длиннее 36 месяцев для оборотки и линии. Если новая сумма ниже минимума продукта, решение становится отказом с объяснением. |
| IV | `NEED_INFO` или встречное предложение | Если положение плохое из-за пустой выручки или возраста меньше 6 месяцев — вопрос клиенту. Иначе сумма режется до нагрузки 0.30. Если так сумма не собирается — отказ. Сотрудник подтверждает этот исход. |
| V | `REJECTED` | Отказ. Причина пишется словами стоп-фактора или фразой «финансовое положение и обслуживание долга не позволяют выдать кредит». |

Объяснение собирается из сработавших факторов шаблоном:

- что проверили;
- что нашли;
- какая вышла категория;
- что это значит для суммы, срока и ставки;
- что делать клиенту дальше.

Один и тот же текст, короче, показывается клиенту. Полный набор факторов показывается сотруднику.

Числовой балл 0–100 нужен для экрана, решение от него не зависит:

```text
score = 100
минус 40, если положение плохое; минус 15, если среднее
минус 40, если обслуживание плохое; минус 15, если среднее
минус 25, если есть стоп-фактор
```

Балл ограничивается диапазоном 0–100.

## 13. Запуск

`docker-compose.yml`:

1. `db` — postgres, volume, healthcheck.
2. `api` — ждёт здоровый `db`, применяет миграции, загружает фикстуры пользователей и моков, слушает порт 8000.
3. `web` — nginx со сборкой Vite, проксирует `/api` на `api`. Порт 8080.

Команда проверки, которую пишем в README и сами прогоняем:

```text
docker compose up --build
```

Дальше открывается `http://localhost:8080`. Отдельная установка Python и Node на машине жюри не требуется.

Повторный `up` не плодит дубликаты тестовых пользователей: сид идемпотентный.

## 15. Сценарии приёмки

Их же кладём в `docs/test-scenarios.md` как скрипт демонстрации.

1. **Одобрение.** Клиент `client.good` подбирает оборотный кредит 1 500 000 ₽ на 18 месяцев, отправляет заявку с ИНН `7700000001` и выручкой, которая держит нагрузку ниже 0.40. Статус сам доходит до «Одобрено». Условия совпадают с запросом. Подписание переводит заявку в «Финансирование оформлено». После обновления страницы статус тот же.
2. **Встречные условия.** ИНН `7700000002`, сумма завышена относительно выручки. Клиент видит меньшую сумму, более высокую ставку и текст, почему так. Принятие ведёт к оформлению. Отказ от условий ставит «Заявка отменена».
3. **Отказ.** ИНН `7700000003`. Клиент видит отказ из-за процедуры банкротства. Сотрудник на своей карточке видит тот же стоп-фактор и сырой ответ мока.
4. **Уточнение.** ИНН `7700000005`. Конвейер останавливается на вопросе о выручке. Ответ клиента возвращает заявку в проверку, появляется новый расчёт, старый остаётся в журнале.
5. **Ручное решение.** Сотрудник открывает заявку категории IV или любую активную, меняет решение комментарием. Клиент после обновления видит новый статус и формулировку сотрудника.
6. **Изоляция.** Клиент А не открывает заявку клиента Б по прямому id: ответ 404 или 403.
7. **Пустой запуск.** Чистое `docker compose up --build` на машине, где репозиторий только что скачан. Сценарий 1 проходит.

Модульные тесты backend, минимум:

- матрица категории на трёх положениях и трёх качествах обслуживания;
- стоп-фактор банкротства даёт V и отказ даже при сильной выручке;
- аннуитет и обратная сумма сходятся: платёж от `max_amount` не выше целевого;
- запрещённый переход, например `ISSUED → DRAFT`, отклоняется;
- рекомендация продукта по четырём целям.

## 16. Документация, без которой решение не считаем готовым

1. `README.md` — что это, как запустить одной командой, учётки, какой сценарий показывать, что смоделировано, ограничения, как решение можно развивать.
2. `docs/state-machine.md` — диаграмма и таблица переходов из раздела 7.
3. `docs/data-model.md` — таблицы из раздела 8.
4. `docs/test-scenarios.md` — раздел 15.
5. `docs/api.http` — живые запросы.
6. `docs/THIRD_PARTY_NOTICES.md` — симуляторы и правовая рамка: БКИ в прототипе синтетический.
7. OpenAPI отдаётся приложением. Файл `docs/openapi.json` коммитится выгрузкой, чтобы его можно было открыть без запуска.

В README отдельно три ограничения:

- подписание и выдача — экранная симуляция;
- внешние проверки — локальные фикстуры;
- скоринг — учебная матрица по мотивам 590-П, не резерв и не IRB.

И три направления развития:

- очередь и асинхронные интеграции вместо синхронного конвейера;
- настоящие адаптеры ЕГРЮЛ и согласие субъекта на БКИ;
- открытая LLM только как перефраз уже готового объяснения, решение по-прежнему считает правиловая модель.

## 17. Порядок работ

Делать в этом порядке. Следующий пункт начинается, когда предыдущий уже проходит свой сценарий.

1. Каркас: compose, пустой API `/health`, пустой фронт, README с командой запуска.
2. Пользователи, JWT, роли, сид учёток.
3. Продукты и рекомендация. Экран потребности и карточек.
4. Черновик заявки и сохранение. Отправка переводит в `SUBMITTED`.
5. State machine и журнал событий. Экран статуса читает журнал.
6. Три мока и фикстуры пяти ИНН. Шаг обогащения пишет `external_checks`.
7. Скоринг и решение. Четыре демо-ИНН дают четыре разных исхода.
8. Экраны результата, уточнения, принятия условий и подписания.
9. Кабинет сотрудника: очередь, карточка, подтверждение, override, запрос уточнения.
10. Тесты скоринга и переходов. Прогон сценариев 1–7.
11. Документы из раздела 16. Выгрузка OpenAPI.
12. Чистый прогон `docker compose up --build` с нуля.

Только после зелёного сквозного сценария имеет смысл добавлять перефраз объяснения открытой моделью. Если модели нет локально, пункт не блокирует сдачу: шаблонное объяснение уже выполняет ту же продуктовую задачу.

## 18. Определение готовности

MVP готов, когда одновременно верно следующее:

1. Сценарии 1–4 проходятся в браузере на тестовых учётках.
2. Обновление страницы не теряет статус, условия и журнал.
3. Сотрудник видит те же данные, что изменили решение, и может их переопределить.
4. `docker compose up --build` на чистой машине приводит к рабочему `localhost:8080`.
5. В репозитории есть README, OpenAPI, диаграмма состояний, модель данных, сценарии и пометки о симуляторах.
6. В коде нет вызовов платных API и нет обращения к реальному БКИ, ЕГРЮЛ или ФНС.
