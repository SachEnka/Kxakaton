# Тестовые сценарии

Пароль всех демо-учёток: `Demo-2026`. Кабинет: http://localhost:8080. Пошаговый показ для жюри (учётки, вводимые данные, действия, ожидаемые статусы и как проверить в интерфейсе) — в [DEMO.md](DEMO.md). Этот файл — перечень того, что нужно проверить, и описание автоматических тестов.

**Статус проверки.** Автотесты и основной сценарий через API выполнены 2026-10-26 (раздел «Результаты фактического тестирования» ниже).

## Ручные сценарии

| № | Что проверяется | Учётка | ИНН | Ожидаемый итог |
|---|---|---|---|---|
| 1 | Одобрение, оформление, подписание, сохранение после F5 | `client.good@demo.local` | `7700000001` | «Одобрено» → «Оформление» → «Финансирование оформлено». Условия по запросу: 1 500 000 ₽ на 18 мес. |
| 2 | Встречные условия: отказ и принятие (две заявки) | `client.offer@demo.local` | `7700000002` | «Есть предложение с другими условиями» → «Заявка отменена» или «Оформление». Предложена меньшая сумма и более высокая ставка |
| 3 | Отказ и вид решения у сотрудника | `client.reject@demo.local`, затем `underwriter@demo.local` | `7700000003` | «Отказано» из-за банкротства; у сотрудника стоп-фактор и сырой ответ источника ФНС |
| 4 | Банк запрашивает уточнение | `client.info@demo.local` | `7700000005` | «Нужны уточнения» → после ответа «Готовим решение». В карточке сотрудника два расчёта |
| 5 | Ручное решение сотрудника | `underwriter@demo.local` | заявка из сценария 4 | Новый статус виден клиенту, комментарий сотрудника показан как объяснение. Демонстрировать только на заявке, прошедшей конвейер (см. ограничение) |
| 6 | Сохранение состояния и черновика | любая клиентская | любой | После F5 те же статус, условия и журнал; черновик открывается на шаге «Данные для заявки» |
| 7 | Изоляция | две клиентские учётки | любой | Чужая заявка: 404 «Заявка не найдена». Клиент на маршруте сотрудника: 403 |
| 8 | Пустой запуск | — | — | В чистом окружении `docker compose up --build`, затем сценарий 1 |

Дополнительно:

- ИНН `7700000004` (ИП): отказ из-за просрочки 120 дней. Отдельной учётки нет, ИНН вводится вручную.
- ИНН `7700000099`: сбой источника, заявка остаётся в «Проверяем сведения о компании». Через интерфейс клиента не воспроизводится (кнопка отправки неактивна, потому что карточка организации не находится), только через API.
- Настоящий ИНН: проверяет карточку организации из открытых сервисов ФНС. Нужен интернет в контейнере `api`, доступность сторонних сервисов не гарантируется.

**Ограничение сценария 5.** Сейчас сотрудник технически может вынести решение по любой незавершённой заявке, в том числе по черновику или по заявке, где конвейер ещё не закончился. Это известный дефект, описанный в [REQUIREMENTS_CHECKLIST.md](REQUIREMENTS_CHECKLIST.md). Исправление в этой версии документов не делалось.

## Автоматические тесты

Каталог `backend/tests/`, настройки в `backend/pytest.ini`. Запуск при поднятом compose:

```text
docker compose exec api pytest
```

**Результат запуска:** 15 passed, 0 skipped, 0 failed (2026-10-26, в контейнере, см. раздел ниже).

| Файл | Тесты | Нужна БД |
|---|---|---|
| `test_rules.py` | матрица категории; банкротство как стоп-фактор; обратный расчёт аннуитета; запрещённый переход; подбор продукта по цели; запись ставки; четыре исхода для демо-профилей | нет |
| `test_egrul.py` | разбор строки открытого поиска ЕГРЮЛ; карточка «Прозрачного бизнеса» из опубликованной выписки; демо-ИНН не обращается к ФНС | нет |
| `test_acceptance.py` | одобрение, подписание и обновление; отказ от встречных условий; отказ по банкротству и видимость сотруднику; уточнение сохраняет прежний расчёт и затем ручное решение сотрудника; клиент не читает чужую заявку | да, PostgreSQL |

Тесты приёмки при недоступной БД пропускаются (`pytest.skip`). Они работают с той же базой, что и приложение (`DATABASE_URL`), и создают в ней заявки. После запуска в очереди сотрудника появятся тестовые заявки, поэтому перед показом жюри лучше прогнать тесты на отдельной базе или запускать показ на чистом томе.
